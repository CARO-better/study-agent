### 2. 建数据库集合

云开发控制台 → 数据库 → 新建集合。

**结论先给：建 12 个，不要建 `credentials`。**

`deployment/database.json` 列了 12 个，但其中 `credentials` 在云函数代码里**引用 0 次**，
`adapters/repository.js` 的 `COLLECTIONS` 白名单里也没有它 ——
API Key 是加密后存进 `providerSettings.keyEnvelope` 的，不需要独立集合。建了也是空表。

反过来，**`snapshots` 是后来加的自动同步必需项**，原始 `database.json` 里没有，要手动补建。

| # | 集合 | 谁在用 | 什么时候会撞上 | 不建会怎样 |
|---|---|---|---|---|
| 1 | `tasks` | records / plan-api / imports / extraction / resources | **核心，随时** | 任务功能全废 |
| 2 | `ownerLocks` | `repository.transaction()` | **任何写操作（增/改/删）** | 全部写操作 `INTERNAL`，但读正常 —— 最易误判的坑 |
| 3 | `semesters` | records / plan-api | 建课程时（`courses.semesterId` 必填） | 建课程失败 |
| 4 | `courses` | records / plan-api / resources | 建课程、任务关联课程 | 建课程失败、任务无法关联 |
| 5 | `profiles` | records / plan-api | 「计划」页生成排期、存个人设置 | 排期失败 |
| 6 | `plans` | plan-api | 「计划」页生成/读取排期结果 | 排期失败 |
| 7 | `planRevisions` | plan-api | 撤销上一次排期 | 撤销失败 |
| 8 | `importDrafts` | imports / extraction / upload-cleanup | 截图或文字识别导入 | 识别导入失败 |
| 9 | `uploadTickets` | upload / upload-cleanup | 上传截图（票据一次性校验） | 截图上传失败 |
| 10 | `providerSettings` | provider-settings / model | 「AI 助理」里配模型 Key | AI 功能报 `PROVIDER_UNCONFIGURED` |
| 11 | `providerUsage` | model / ocr / ai-chat | AI/OCR 的每日调用限流 | AI 调用失败 |
| 12 | `snapshots` | **`sync.pull` / `sync.push`** | **自动同步（每用户一条完整快照）** | 数据不会自动上云/恢复 |
| — | ~~`credentials`~~ | **无人使用** | 永远不会 | 无影响，**不用建** |

**一次性全建的价值**：建一个集合是几秒钟的事；而少一个，报错会被云函数压成 `INTERNAL`，
排查成本远高于建集合。你现在只差 10 个，一次建完以后不用再回来。

#### 索引（建完集合顺手建）

控制台 → 选中集合 → 索引管理 → 新建，字段全部**升序 1**，唯一性全部**否**。

| 集合 | 索引字段 |
|---|---|
| `tasks` | `ownerOpenId`+`_id`；`ownerOpenId`+`courseId`+`_id`；`ownerOpenId`+`parentTaskId`+`_id`；`ownerOpenId`+`status`+`_id` |
| `courses` | `ownerOpenId`+`_id`；`ownerOpenId`+`semesterId`+`_id` |
| `semesters` | `ownerOpenId`+`_id` |
| `profiles` | `ownerOpenId`+`_id` |
| `plans` | `ownerOpenId`+`_id` |
| `planRevisions` | `ownerOpenId`+`_id` |
| `importDrafts` | `ownerOpenId`+`_id` |
| `providerSettings` | `ownerOpenId`+`_id` |
| `providerUsage` | `ownerOpenId`+`_id` |
| `uploadTickets` | `ownerOpenId`+`_id` |
| `snapshots` | `ownerOpenId`+`_id` |
| `ownerLocks` | **无索引**（只按 doc id 读写） |

为什么需要索引：`repository.list()` 的查询是 `.where({ ...query, ownerOpenId }).orderBy('_id','asc')`。
带 `orderBy` 的复合条件在云数据库里缺索引会报「没有可用索引」，数据量小时可能侥幸能跑，
数据一多就变成偶发失败 —— 属于最难查的那类问题。

**⚠️ 写操作必须同时存在 `ownerLocks`，否则一定失败。**

`repository.transaction()` 每次写都要先写 `ownerLocks` 做并发闸门：

```js
const guard = transaction.collection('ownerLocks').doc(docId(owner, 'lock'));
…
await guard.set({ data: { ownerOpenId: owner, version: (old?.version || 0) + 1, updatedAt: now() } });
```

**这个集合不存在时，事务整体回滚，错误被压成 `INTERNAL`** —— 表现是「`tasks.list` 读得到、`tasks.create` 写不进」，
非常容易误判成代码问题。`ownerLocks` 的安全规则是 `{read:false, write:false}`，客户端完全禁止，只有云函数能碰。

| 场景 | 至少要建的集合 |
|---|---|
| 只传任务（无课程） | `tasks` + **`ownerLocks`** |
| 传学期/课程/任务 | `semesters` + `courses` + `tasks` + **`ownerLocks`** |
| 完整功能 | 12 个全建 |

其余集合（`importDrafts`、`providerSettings`、`plans` 等）等用到对应功能时再补。

索引建法：控制台 → 选中集合 → 索引管理 → 新建，字段全填**升序 1**，唯一性按上表（全部非唯一）。

### 4. 迁移（单向上传已实现）

设置页现有三个按钮，按顺序用：

| 按钮 | 作用 | 是否写数据 |
|---|---|---|
| 检测云端连接 | 调 `system.ping` + `tasks.list`，报运行时和集合状态 | 否 |
| 预览上云内容 | `migrate.buildPlan()` 转换并列出问题 | 否 |
| 上传到云端 | 确认后执行 `migrate.upload()` | 写云端 |
| 从云端恢复 | `migrate.restore()` 拉回云端数据并覆盖本地 | 写本地 |

**「从云端恢复」是清缓存 / 换手机后的救命按钮**：它并行拉 `semesters` / `courses` / `tasks`，
把云端结构反向转回本地 store（`semesterId` → 学期名、`assignment` → `homework`、ISO 时间 → `YYYY-MM-DD`、
指向已删课程的 `courseId` 自动断开），然后覆盖本地。

三条本地数据的命运不一样，必须分清：

| 本地键 | 内容 | 上传过？ | 恢复得了？ |
|---|---|---|---|
| `study_trial_v1` | 课程 / 任务 | ✅ | ✅ 点「从云端恢复」 |
| `study_ai_v1` | 模型 API Key | ❌ **从没上传** | ❌ 只能重填 |
| `study_inbox_v1` | 站内消息 | ❌ | ❌ 重新生成 |

**为什么 Key 不能从云端恢复（架构原因，不是漏做）**：

现在 AI 是**前端直连模型**——`lib/ai.js` 拿着明文 Key 从手机直接请求服务商。
云端 `providerSettings.keyEnvelope` 存的是 AES 密文，是给**云函数代理调模型**那条链路准备的，
前端没有主密钥，解不开，也就没法还原成明文。

要彻底解决「清缓存丢 Key」，得把 AI 调用改成走云函数：
`providers.save` 存加密 Key → 云函数解密后代为请求 → 前端只发 prompt 不碰 Key。
这是架构改动，不是加个按钮能解决的，见下方「还没做的」。

**上传流程**：问题未清零会直接拦截 → 逐个学期确认日期（可用推断值，也可手填「开始,结束,周数」）→
汇总确认 → 带进度的上传 → 报告成功/失败条数。

**三条保证**：
1. **本地数据一个字节都不动**，云端存副本（`study_cloud_migrated_at` 记时间戳）
2. **顺序强制** `semesters → courses → tasks`，id 映射在内存里逐层传递
3. **失败降级**：某门课失败不会让它的任务丢失，任务照传、只解除课程关联

**仍然存在的限制**（诚实列出，别当成已解决）：

- **多设备同时改会互相覆盖**：整份快照按 `updatedAt` 后写胜，没有字段级合并。两台设备交替编辑会丢改动。
- **800ms 推送窗口**：改完立刻强杀进程，最后一次改动可能来不及推（`onHide` 已尽量 flush）。
- **记录级同步仍未做**：日常同步走 `snapshots` 快照；云端 `courses` / `tasks` 集合只有旧的「上传」按钮会写。
  以后要多端协作、云端统计或按条件查询，得改回逐条同步（届时要处理 id 映射与删除队列）。
- **排期仍在本地算**：`plans` / `planRevisions` 集合依旧是空的。

仍需注意的 **3 个硬障碍**：

**① id 不能通用 —— 这是最大的坑**

```js
// 云函数 core/records.js:64
const record = previous ? {...previous, ...selected} : { ...selected, id: deps.newId() };
```

后端用 `randomUUID()` **自己生成 id**，而 `select()` 只挑白名单字段，**前端传来的 id 会被丢掉**。
本地 `uid()` 生成的 id（如 `m3k9x2a1`）和后端 UUID 是两套体系。

→ 迁移必须建 id 映射表：先传 course，拿到后端 id，再回填到 task 的 `courseId`。
   顺序只能是 **semesters → courses → tasks**，反过来会被 `INVALID_REFERENCE` 拒。

**② 学期模型对不上**

本地把学期名存成课程的一个字符串字段（`courses[i].semester`），后端要求独立的 `semesters` 记录 +
`courses.semesterId` 引用，且 `semesterId` 是**必填**。

→ 迁移前要先从本地课程里提取去重的学期名，造出 semesters（需要 `startDate` / `endDate` /
   `teachingWeeks`，本地完全没有这些字段，只能让用户补填或给默认值）。

**③ 枚举不一致**

| 本地 | 后端 |
|---|---|
| `status: 'open'` | `pending` / `in_progress` |
| `type: 'homework'` | `assignment` |

`lib/cloud.js` 已导出 `STATUS_LOCAL_TO_SERVER` / `TYPE_LOCAL_TO_SERVER` 两组映射，直接用。
另外 `tasks.remainingMinutes` 后端是**必填整数**（0–100000），本地 `saveTask` 限制的是 1–10000，
迁移时要按后端规则重新校验。

**建议的迁移步骤**

1. 先在设置页点「检测云端连接」，确认 `ok: true`
2. 建 4 个集合（`profiles` / `semesters` / `courses` / `tasks`）
3. 写一次性迁移脚本：本地 store → 后端，过程中维护旧 id → 新 id 映射
4. 迁移后 `today` 改成双读：云端优先，云端失败回落本地，并在界面标出当前数据源
5. 全部稳定后再关掉本地写

### 5. 云函数环境变量（用 AI 功能前必须配）

`STUDY_MASTER_KEY` **不是去哪里找的，是自己生成的**。它是 AES-256-GCM 的对称主密钥，
用来加密你填的模型 API Key，加密结果存在 `providerSettings.keyEnvelope` 里。

**生成（在自己终端跑，不要用在线随机工具）：**

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

产出 **44 个字符**，末尾常带 `=`。`core/vault.js` 会做两项校验，任意一项不过就抛 `Invalid master key`：

| 校验 | 说明 |
|---|---|
| 解码后正好 32 字节 | `k.length !== 32` |
| 回编码与原文完全一致 | `k.toString('base64') === raw`，所以不能有空格、换行、url-safe 变体 |

**填哪**：云开发控制台 → 云函数 → `api` → 配置 → 环境变量 → 新增

- 名称：`STUDY_MASTER_KEY`
- 值：上面生成的整串（含末尾 `=`）

保存后**重新部署一次云函数**，确保新实例读到新值。

**三条注意：**

1. **不要写进项目文件、不要提交 git**。`miniprogram/config.js` 是前端代码，只能放 `envId`（本身不敏感）。
2. **自己留一份记录**。丢了不影响课程/任务数据，但 `providerSettings` 里已加密的 Key 解不开，只能删掉重填。
3. **暂不用 AI 可以先不配**。只有 `providers.save` / `providers.test` 这条链路依赖它。
   没配时保存 Key 的表现是 `INTERNAL 服务暂时不可用`（底层 `Invalid master key` 被压成了 INTERNAL）。

### 6. 自动同步与云端代理（已实现）

> 从这一节起，「上传/恢复」按钮变成兜底手段，日常使用是全自动的。

#### 同步机制：整份快照

`lib/sync.js` + 云函数 `core/snapshots.js`。每个用户在 `snapshots` 集合里固定一条记录（`id='default'`），
`payload` 是完整 store。

**为什么不做逐条同步**：本地 id 由 `uid()` 生成，后端用 `randomUUID` 且会用 `select()` 丢弃前端 id，
两套 id 体系要同步就得维护映射表 + 删除队列 + 逐条版本比对，任何一处错都会**静默丢数据**。
整份覆盖是原子的，不存在「同步了一半」；代价是**多设备同时改会互相覆盖**（按 updatedAt 后写胜），
对单人单设备可接受。

**时机**

| 场景 | 行为 |
|---|---|
| 本地任意改动 → `save()` | 立即标记本地时间戳，800ms 防抖后把整份 store 推上云 |
| 页面隐藏 / 切后台 → `onHide` | `flush()` 立刻把待发的推出去，不等防抖 |
| 启动 → `onLoad` | 先用本地渲染（不等网络），再异步 `sync.pull` |
| 拉取后判断 | `sync.decide()`：云端更新则覆盖本地并 toast 提示 |

**冲突判断**（`sync.decide`，纯函数，5 种情况都已单测）：

```
云端无数据          → local
本地为空（清缓存）   → remote   ← 这就是「清缓存后自动恢复」
本地无时间戳        → remote
云端 updatedAt 更新 → remote
本地 updatedAt 更新 → local
```

推送成功后用**服务端返回的 `updatedAt`** 回写本地时间戳，避免手机时钟不准导致的判断错位。
